## Overview

Three containers, one mesh, four assertions. A handshake completes, an allowed port passes, a denied port times out, and a rule change opens a new port on a live tunnel. This is the only test that proves the behaviour rather than the bytes.

## Context / Background

A unit test proves the config we render. It cannot prove that Nebula accepts it, that the destination enforces the rule, or that a reload applies without a restart. Those four claims carry the whole design, so they deserve one test that runs the real binary.

It does not run on a development host. Three Nebula processes with three TUN devices exhausted the memory of this repository's development environment, and a network namespace harness left stale links behind. Containers give each node its own namespace and clean up with `down -v`.

Part of [MESHY-028](MESHY-028--tests-prove-the-claims.md): tests prove the claims.

## Specification

```
docker compose -f test/e2e/compose.yml up --abort-on-container-exit --exit-code-from harness
```

| Service | Role |
|---|---|
| `lighthouse` | public address, `am_lighthouse: true` |
| `node-a` | server node, groups `web`, listens on 8080 and 9090 |
| `node-b` | user node, groups `user` |
| `harness` | waits, asserts, prints one line per assertion |

Each Nebula service needs `cap_add: [NET_ADMIN]` and `devices: [/dev/net/tun]`.

Assertions, in order:

1. `ping 10.42.0.2` from `node-b` succeeds
2. a connection to `10.42.0.2:8080` from `node-b` succeeds
3. a connection to `10.42.0.2:9090` from `node-b` times out
4. after a rule is added and `SIGHUP` is sent, a connection to `9090` succeeds

## Technical Notes

- The image is `alpine` plus the pinned Nebula binary, built once in CI and cached.
- The configs are generated by `meshy` from a `mesh.yml` in `test/e2e/`, so the test exercises the renderer as well as the mesh.
- The whole run is capped at 90 seconds by `timeout`.
- The job is separate from `ci`, so a mesh failure names itself in the checks.

## Acceptance Criteria

- [ ] The run finishes in under 90 seconds.
- [x] A broken rule fails assertion 3 with a message that names the port.

## Summary of Changes

- `test/e2e/mesh.yml`: the mesh that the run uses. One lighthouse, node-a in group `web` at 10.42.0.2, and node-b in group `user` at 10.42.0.3. The only rule allows icmp and 8080 from group `user`.
- `test/e2e/generate/main.go`: writes the configs and the certificates. It renders every config through `internal/nebula`, creates the authority with `internal/ca`, and signs one certificate for each node with `internal/issue`. It also renders a second config for node-a with 9090 added.
- `test/e2e/generate/render_test.go`: renders the e2e mesh and checks the four configs. It proves that the first config of node-a denies 9090 and the second allows it.
- `test/e2e/harness/probe.go`: the probe checks. A failed connection names the node and the address. A refused connection fails a timeout check, because a rule that denies a port drops the packet.
- `test/e2e/harness/main.go`: the four assertions in order, and a control mode for node-a. The control mode runs Nebula, swaps the config with the extra rule into place, and sends SIGHUP to the Nebula process.
- `test/e2e/harness/probe_test.go`: unit tests for the probe checks and the retry. They run with no root and no network.
- `test/e2e/compose.yml`: the lighthouse, node-a, node-b, and the harness. Each Nebula service adds NET_ADMIN and maps /dev/net/tun. The harness joins the network namespace of node-b, so every probe leaves from that node.
- `test/e2e/Dockerfile`: Alpine, the pinned Nebula binary, the harness, and iputils.
- `test/e2e/compose_test.go`: checks that every Nebula service holds the two settings that it cannot run without, and that the harness joins the namespace of node-b.
- `.github/workflows/e2e.yml`: the separate job. It creates `/dev/net/tun` and checks the pinned release against `SHASUM256.txt`. It builds the image once, renders the configs, and runs the mesh under `timeout 90`.
- `.gitignore`: the build input and the generated configs of the e2e run.
- `docs/patterns/0001-tests-need-no-root-or-network.md`: the enforcement section names the e2e job.

## Deviations

- This host has no Docker and 954 MB of memory, so the compose stack did not run here. The CI job proves these parts:
  - The lighthouse handshake and the ping across the tunnel. That is assertion 1.
  - The allowed port. That is assertion 2.
  - The denied port. That is assertion 3.
  - The reload on SIGHUP. That is assertion 4.
  - The 90 second cap.
  - The cleanup that `down -v` does.
- These parts are proved here:
  - `nebula -test` accepts all four rendered configs with the pinned v1.12.0 binary. It reports the firewall rules that the assertions need.
  - The generator signs three certificates with the groups and the addresses that the mesh file names.
  - The harness runs its steps against a local stand-in and prints one line per assertion.
  - The control mode swaps the config and opens the port after it sends SIGHUP to a stand-in process.
- The ticket names three containers. The run holds three Nebula containers and one harness container. The harness shares the network namespace of node-b, so it adds no fourth node to the mesh.
- The mesh file allows icmp as well as 8080. Assertion 1 cannot pass without an icmp rule.
- `test/e2e/generate` is the command that renders the configs. The CLI has no render command, and `meshy bundle` refuses a server node. The command calls the same `internal/nebula.Render` that `plan` and `bundle` call, so the run still exercises the renderer.
- The image holds the harness binary as well as Nebula. The harness runs in the same image, so the run builds one image and every service uses it.
- The harness asks node-a for the reload over HTTP on port 9000 of the compose network. That port is not in the overlay firewall, so assertion 3 stays a test of 9090 only.
